## 4. 正式发布前必须补齐的部分

| 缺少发布包与传输契约 | 现有工具没有 SSH 交付、资源清单、远端接收校验或上传中断处理 | 固定包内容、manifest、完整文件校验；上传暂存完成后再交付安装 |

| 发布过程切流较多 | 当前 new → old → new；候选 App 在 worker 晋升时重启 | 评估改为备用槽位验证与晋升均不承载入口流量，再做一次正式切流，减少连接反复排空 |
| 排空与后台任务限制未针对 Babel 重新验收 | 常规发布默认排空 120 秒；Nginx 超时 600 秒；App Shutdown 仅 5 秒 | 明确长流等待/超时策略、worker 短暂重叠边界和主机容量；不强停活跃请求，不承诺绝对零停机 |
| 回滚只处理应用与入口 | repository/ent.go 在应用初始化时执行 SQL migrations | 发布前比较迁移、评审旧版本兼容性；不兼容迁移必须进入单独维护流程，不能只回切二进制 |

## 5. 建议的最小目标流程（待讨论定稿）

```text
Genesis：已提交并推送的确定版本
  → 隔离导出源码并构建
  → 发布包：应用 + 必要资源 + manifest / 校验值
  → SSH 上传到 Babel 暂存区

Babel：Agent 以普通用户命令调用受限发布入口（首次授权由用户安装）
  → 校验主机、包内容、版本、迁移风险、资源和当前槽位
  → 安装到不可变 release，配置备用槽位
  → 备用槽位检查，完成 worker 晋升
  → 一次正式切流，验证入口与版本
  → 等待旧连接结束，再停旧 App
  → 记录结果，保留上一 release 供显式回滚
```

部署器不接受发布包内任意脚本作为 root hook，不传生产密钥、不覆盖数据库 / Redis / general 配置、不借应用发布重启数据服务。每次构建使用的临时目录自动退出清理，不重新积累长期 worktree。

## 6. 用户新增约束：失败保护与 Agent 无交互发布

用户要求：切换过程失败能够回滚、不影响服务；调用发布脚本本身不需要 sudo，内部可执行指定的 sudo 操作，让所有 Agent 都能调用。下述权限方向已按此要求调整；“任意故障下绝对没有请求失败”不能作为单机脚本的可兑现承诺，保障边界仍需用户确认。

### 权限与入口

- 拟提供普通用户命令 `vsp-release deploy <release-id>`、`vsp-release status` 和 `vsp-release rollback`；这些命令尚未实现，不是现在可执行的接口。
- 外层负责构建、上传或查询；在 Babel 通过 `sudo -n` 调用 root 所有的固定执行器。一次性安装 sudoers 后不再逐次要求用户输入密码，不依赖 sudo 的临时凭据缓存。
- 只授权受限发布 / 回滚入口，不开放任意 systemctl、shell、路径、unit、环境变量或包内 root hooks。发布包的二进制仍以应用普通用户身份运行。
- root 执行器、依赖、配置与整个父目录链必须不可被普通用户替换。当前 Babel release / slot 目录可被 heyx 写入，需要在安装阶段明确调整所有权边界；应用运行数据保持独立可写。
- sudo 按 Unix 用户 / 组授权，不识别 Agent 身份。同属 heyx 且具备 Babel SSH 访问的 Agent 可以共用入口；同账号其他进程也拥有相同发布入口权限。不同账号需要显式加入授权范围。
- 权限只意味着可以调用受限部署功能，并不保证候选应用没有业务错误或无法修改其本来有权访问的数据库。

### 失败保护设计方向（尚未实现）

| 场景 | 目标行为 / 前提 |
| --- | --- |
| 构建、上传、校验、备用启动失败 | 不修改当前流量目标、不重启旧实例；候选需有资源上限并限制初始化副作用 |
| Nginx 配置检查 / reload 失败 | 保留或恢复旧配置；同时验证磁盘入口和实际生效路由，不能只读 symlink |
| 切流后候选健康失败 | 旧实例在观察窗口内仍可接管新请求，自动回切并验证结果；不能挽回已失败的请求或已中断流 |
| 长连接或入口已接收的请求未结束 | 不强停仍有请求的进程；排空验证须覆盖旧 Nginx worker 尚未转发的请求，不能只依赖 App 端口的瞬时连接数；超时按失败/待处理结果退出，不假装成功 |
| SSH 断开、Agent 退出 | Babel 由独立 systemd 服务承载发布任务；不是依附 SSH 会话的前台 shell |
| 发布执行器异常退出 | 根据最小持久化记录由受监督恢复逻辑处理，不能只依赖 shell trap；恢复失败须明确报错 |
| 多 Agent 并发发布或回滚 | 主机级锁排他，后一个请求不得修改进行中的候选、槽位或记录 |
| 数据库迁移或数据格式不兼容 | 在候选连接生产数据库前拦截普通自动发布，进入单独审阅和备份/恢复流程 |
| 后台任务重复执行 | 必须解决任务所有权交接；仅保留两个带 active worker 的实例并不能满足无副作用目标 |

现有确定缺口：`deploy-app-release.sh` 在 `committed=true` 后停止旧 App，再执行最后健康检查；最终检查失败没有完整自动回滚分支。`wire.go` 的 autonomous worker 开关在服务创建/启动阶段生效，现有能力不能直接实现旧实例保持热备用且同时转为不执行后台任务的状态。必要的后台任务协调属于发布安全的基础设施改动，不应与后续 UI / 国模功能微调混为一谈。

建议验收采用故障注入矩阵：坏包、复制失败、端口占用、候选崩溃、Nginx 失败、SSE / HTTP/2 / 慢上传排空、长流超时、并发调用、SSH 中断、执行器被终止、不可兼容迁移和非法提权参数。每项同时检查旧服务、实际入口、活动请求、后台任务与最终记录；静态检查和单次 health=200 不足以证明发布安全。

边界：单台 Babel 上的主机故障、共享数据库故障、候选应用错误导致已接受请求失败，无法靠入口回滚消除。即便切流前候选不承载公网请求，共享数据库及主机资源也可能被其初始化影响，所以还需要迁移门禁、任务隔离和资源约束。若用户要求任何上述故障下都零失败请求，必须重新讨论架构和可实现的 SLO，不能直接承诺当前蓝绿脚本能够做到。

参考：[Nginx 平滑重载行为](https://nginx.org/en/docs/control.html)、[sudo 官方权限模型源码](https://github.com/sudo-project/sudo/blob/main/docs/sudoers.mdoc.in)，以及本机安装的 `systemd-run(1)` 手册（service 模式由 service manager 独立管理，与 scope 模式不同）。
